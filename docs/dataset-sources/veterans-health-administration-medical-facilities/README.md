These 2026-11-14 checks describe this endpoint family, not every official way to inspect facility data:
  - **Key-gated**: `GET /facilities?per_page=1` without credentials answers HTTP 401 `{"message":"No API key found in request"}`; `/ids` and `/facilities/all` answer HTTP 401; the sandbox host `sandbox-api.va.gov` is equally key-gated and serves only test data. Obtaining a key requires registering at developer.va.gov ("third party seeking access ... will need to complete a quick application to obtain an API key", per the VA `vets-api-clients` README) — an access grant the factory cannot self-obtain.
  - **Publicly verifiable contract without a key**: the production OpenAPI document `https://api.va.gov/internal/docs/facilities/v1/openapi.json` is anonymously readable (HTTP 200, title "VA Facilities", version 1.0.0). Facility IDs are `prefix_stationNumber` (e.g. `vha_402GA`, `vc_0872MVC`) — the same VAST station-number scheme the HIFLD layer's `STA_NO` uses (3-character parents, 5-character CBOC/support sites, 7-character satellites). Health facilities carry `facilityType: va_health_facility` with `lat`/`long`, addresses, `visn`, hours and services.
  - **Scope requires an explicit comparison with HIFLD**: the API covers *active* facilities of all administrations (health `vha`, benefits `vba`, cemeteries `nca`, vet centers `vc`), includes mobile facilities with an explicit "latitude/longitude and address could be inaccurate" warning, and drops null fields from responses; the HIFLD layer covered VHA sites (VA hospitals, RRTP, NHCU, outpatient clinics, Vet Centers, VAMC), excluded planned/suspended non-operational sites and mobile clinics, and carried NGA-requested text normalisation. A faithful selection/filter and station-ID mapping must be evaluated before deciding whether the result is a continuation or materially changed product; simply using every API administration is not a valid replacement. Release notes (`https://developer.va.gov/explore/api/va-facilities/release-notes`): v1 launched 2023-08-24; v0 deprecated 2024-01-01 and deactivated 2024-06-17 (production v0 routes answered HTTP 404); the documented Lighthouse `/facilities` page maximum is 1000, **not an established limit for the public locator endpoint below**. data.gov lists "VA Facilities API" as a Department of Veterans Affairs dataset with catalog update 2026-08-11 (listing previously read via an index, not direct payload verification).

## Verified anonymous first-party route — 2026-11-15

The official [Find VA locations](https://www.va.gov/find-locations/) application was exercised in a browser without signing in, obtaining a developer API key or using a mirror:

1. Enter ZIP `20001` and select the Washington, DC suggestion.
2. Choose **VA health** and **All VA health services**, then **Search**.
3. Inspect the application's own `POST https://api.va.gov/facilities_api/v2/va` response. It returned HTTP **200**, ten rows, and `meta.pagination` containing `currentPage=1`, `nextPage=2`, `totalPages=2`, `totalEntries=20` for the regional search. All ten inspected rows had `lat`/`long` coordinates.

The response preserves IDs such as `vha_688` (Washington VA Medical Center) and string `uniqueId="688"`, plus `facilityType`, `classification`, `lat`, `long`, physical address, `mobile`, `visn`, `operatingStatus`, hours and service information. This demonstrates access to real source records and a candidate station-ID mapping. It does **not** establish parity with the historical layer's fields or IDs, a complete national population, or data freshness for every facility. A `services.health.lastUpdated` value is service metadata, not necessarily a coordinate or facility-record update date.

The production bundle linked by the VA page, `https://prod-va-gov-assets.s3-us-gov-west-1.amazonaws.com/generated/facilities.entry.js`, names the same endpoint and uses a POST search with `type`, `page`, `per_page`, `mobile` and location/bounds parameters. The checked application chooses page size 10 and `mobile=false` for health searches. The captured response's JSON uses camel-case attributes; preserve the actual chosen source representation rather than assume the Lighthouse schema is byte-identical.

This is a normal anonymous application session, **not a credential-free bare HTTP API contract**: a direct GET to the search endpoint returned route-not-found, and a standalone POST without the normal application session returned HTTP 403 `Invalid Authenticity Token`. The successful browser request uses the site's normal session/CSRF handling; no access control was bypassed. Session tokens/cookies were neither published nor committed, and no provider account was created. Only the public URLs, bounded response facts and reproduction flow are recorded here; browser inspection is not a durable full-population capture or independently replayable extraction bundle.
